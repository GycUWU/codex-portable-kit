# Technical Document Review Checklist

## Evidence

- [ ] Every major behavior is supported by available sources.
- [ ] Inference is not presented as fact.
- [ ] Branch/version context is clear.
- [ ] Comments are not treated as stronger than executable behavior.
- [ ] External standard behavior is not confused with project behavior.

## Code accuracy

- [ ] Function/field/macro names are exact.
- [ ] Caller/callee relationship is correct.
- [ ] State mutation is described accurately.
- [ ] Error/return behavior is correct.
- [ ] Configuration mapping is correct.
- [ ] Units and conversions are checked.

## Algorithm

- [ ] The problem is stated before the formula.
- [ ] Variables and units are defined.
- [ ] Coordinate/sign conventions are explicit.
- [ ] Assumptions are stated.
- [ ] Math is mapped to code.
- [ ] Numerical limitations are mentioned where material.

## Reader usefulness

- [ ] The reader can locate the implementation.
- [ ] The runtime flow is understandable.
- [ ] Tables are used only where comparison/mapping helps.
- [ ] Code excerpts are short and relevant.
- [ ] Diagrams, if any, reveal real structure.

## Language

- [ ] No repetitive canned introduction.
- [ ] No mechanical “首先/其次/最后” sequence unless needed.
- [ ] No empty importance claims.
- [ ] Paragraph lengths are not mechanically uniform.
- [ ] Summary sections add value instead of repetition.
- [ ] Tone is precise rather than promotional.

## Final

- [ ] Unsupported claims are removed or qualified.
- [ ] Terminology is consistent with the project.
- [ ] The document answers the user's requested scope.
