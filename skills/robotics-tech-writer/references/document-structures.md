# Document Structures

Choose the smallest structure that fully explains the subject.

## A. Feature implementation

1. Purpose and problem
2. External behavior
3. Relevant modules/files
4. Core data structures/state
5. Execution flow
6. Key functions
7. Important algorithm or formula
8. Error/boundary handling
9. Configuration and dependencies
10. Validation or example
11. Practical modification points

## B. Algorithm explanation

1. Problem the algorithm solves
2. Intuition / geometry / physical meaning
3. Inputs, outputs, assumptions
4. Mathematical derivation or model
5. Numerical method
6. Mapping to code variables
7. Runtime procedure
8. Boundary cases and failure modes
9. Example
10. Accuracy / complexity / tradeoffs when established

## C. Architecture overview

1. System responsibility
2. Module boundary
3. High-level flow
4. Folder/file responsibility map
5. Key interfaces
6. Data and control flow
7. Initialization/runtime/shutdown
8. Extension points
9. Risks or coupling

## D. Bug analysis

1. Symptom
2. Impact and reproduction condition
3. Expected vs actual
4. Evidence
5. Root cause
6. Why the old logic failed
7. Fix
8. Behavioral difference after fix
9. Regression risk
10. Verification

## E. Usage guide

1. Prerequisites
2. Inputs/configuration
3. Procedure
4. Expected result
5. Diagnostics
6. Common errors
7. Safety/boundary notes

## F. Learning note from code

1. Concept
2. Why it exists in this project
3. Minimal theory
4. Where it appears in code
5. Walkthrough
6. Example
7. Questions/checkpoints

## Avoid template worship

Delete sections that do not add information.
Add sections when the implementation requires them.
Do not manufacture “advantages”, “future outlook”, or “summary” sections unless requested or genuinely useful.
